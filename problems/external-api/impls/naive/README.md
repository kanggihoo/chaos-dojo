# naive: 외부 상품 API의 응답을 오래 기다린다

## 겨냥하는 요구사항

naive가 지키려는 것은 불변 조건이다([problem README의 요구사항](../../README.md#요구사항)). lookup이 돌려준 가격으로만 주문을 만들고, lookup 응답이 없으면 주문을 저장하지 않는다.

포기하는 것은 장애 중의 SLO와 응답 시간 상한이다. lookup이 느려지거나 죽었을 때 따로 대응하지 않고, 응답이 올 때까지 넉넉하게 기다린다. 장애가 주문 API 전체로 번지는 것도 막지 않는다.

## 왜 이 방식인가

naive는 대응하지 않았을 때를 기록하는 비교 기준이다. timeout을 비롯한 다른 impl이 "이 대응을 넣으면 무엇이 좋아지는가"를 보여 주려면, 대응이 없을 때 어떻게 되는지가 먼저 기록되어 있어야 한다.

이 모습은 많은 서비스가 처음 만드는 모습이기도 하다. HTTP 클라이언트의 넉넉한 기본값을 그대로 쓰거나, 느려도 결국 응답은 오리라고 가정한 코드가 여기에 해당한다.

## 작동 원리

공통 앱(`../../app`)을 `IMPL=naive`로 실행한다. timeout impl과 같은 이미지이고, lookup 호출 설정만 다르다. 값은 같은 폴더의 [`impl.yaml`](impl.yaml)이 정하고, 출처는 [PROVENANCE.md](PROVENANCE.md)에 있다.

naive는 lookup 응답을 최대 10초까지 기다린다. 그 전에 HTTP client pool에서 연결을 얻는 데 최대 2초, 연결하는 데 최대 1초를 쓸 수 있으므로, lookup 호출 하나가 가장 오래 걸리면 13초다. 기다리는 동안 그 요청은 Tomcat 업무 스레드 하나를 붙잡는다. 업무 스레드는 50개이고, HTTP client pool도 50개다.

lookup이 2초 느려지면, 초당 50건이 들어오는 주문을 처리하는 데 업무 스레드가 동시에 100개 필요하다. 스레드가 50개뿐이므로 남은 요청은 accept 큐에서 기다리고, 큐에서 기다린 시간이 lookup의 2초에 더해진다. HTTP client pool에서 2초 안에 연결을 얻지 못한 요청은 503으로, 응답 대기 10초를 넘긴 요청은 504로 실패한다.

응답 대기 한도를 무한으로 두지 않고 10초로 정한 이유는 측정 때문이다. 앱이 끝없이 기다리면 k6가 15초에 요청을 먼저 끊고, 그러면 실제 지연 시간이 기록되지 않고 잘린다. 그래서 최악의 13초도 k6의 15초보다 짧게 맞췄다(experiment-harness decisions.md D-19).

관리 포트(readiness, Prometheus)는 업무 스레드와 별도의 스레드로 응답한다. 그래서 업무 스레드가 모두 막혀도 하네스는 지표를 계속 수집할 수 있다.

## 해결하는 것과 해결하지 못하는 것

해결하는 것은 lookup이 정상일 때의 주문이다. lookup이 빠르게 응답하면 10초 한도에 닿지 않으므로, 대응이 없어도 주문은 정상으로 처리된다.

해결하지 못하는 것은 느린 lookup이 주문 API 전체를 늦추는 일이다. 요청 하나하나가 업무 스레드를 오래 붙잡아 스레드가 바닥나고, 그 뒤에 들어온 요청은 lookup이 아니라 큐 때문에 늦어진다. 기다리다 지친 클라이언트가 먼저 끊은 요청의 주문이 서버에 저장되는 ambiguous outcome도 생긴다.

결과 해석을 바꾸는 수치: api-slow의 장애 구간에서 naive의 201은 1,482건이었지만 500 ms 안에 끝난 201은 1건뿐이었다(20261031-004309-external-api-api-slow-naive-2c0c93, 2026-11-13, repeat별 구간 값에서 중앙값을 직접 구함). 오래 기다려서 받아 낸 201은 사용자에게는 실패와 같다.
