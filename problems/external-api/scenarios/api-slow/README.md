# api-slow: 외부 상품 API가 40초 동안 2초씩 느려진다

## 브리핑

### 상황

주문 API가 lookup에 가격을 물으면, 평소에는 바로 오던 응답이 2초 늦게 온다. lookup은 죽지 않았고 연결도 되며, 결국 정상 응답을 돌려준다. 실제 서비스로 치면 외부 상품·재고 API가 과부하로 느려진 상황이다.

k6가 초당 50건의 주문을 일정하게 보낸다. 30초 warmup 뒤 120초 동안 측정하고, 측정 시작 40초 뒤부터 80초까지 40초 동안 lookup이 느려진다. k6는 15초 안에 응답을 받지 못한 요청을 끊는다. 이 밖의 설정은 같은 폴더의 [`scenario.yaml`](scenario.yaml)에 있다.

이 장애 유형을 고른 이유는 느린 의존성이 죽은 의존성보다 위험할 수 있기 때문이다. 연결이 거부되면 요청이 바로 실패하지만, 응답이 늦으면 요청이 업무 스레드를 붙잡은 채 기다린다. 이 scenario는 외부 API 하나가 느려질 때 주문 API 전체가 같이 느려지는지, 그 기능만 빠르게 실패하는지를 묻는다.

### 클리어 조건

repeat 하나가 아래를 모두 만족하면 클리어다. 기준은 하네스 판정과 같다([problem README의 요구사항](../../README.md#요구사항)).

- repeat가 complete이고 measurement validity가 valid다.
- SLO: measured 요청 전체 가운데 500 ms 안에 201로 끝난 요청의 비율이 0.99 이상이고, 201의 p99가 500 ms 이하다.
- 회복 조건: 장애 해제를 확인한 뒤 60초 창 안에 예산 안 201이 연속 5번 도착한다.
- 불변 조건: 확인된 위반이 없고 증거가 완전하다. ambiguous outcome은 위반으로 세지 않고 따로 보고된다.

lookup 응답이 있어야만 주문을 만드는 impl로는 이 scenario의 SLO를 클리어할 수 없다. 장애 40초는 measured 120초의 3분의 1이고, 그동안 발행한 요청은 500 ms 안에 201을 받을 수 없다. 그래서 예산 안 201 비율은 최대 약 0.67로, 0.99에 못 미친다. naive와 timeout은 둘 다 이런 impl이다.

### 보조 목표

하네스가 판정하지 않음. 사람이 리포트의 장애 전·중·후 구간 값을 보고 판단한다.

- 장애 중: 실패가 빨리 돌아온다. k6 요청 timeout이 0건이고, 201이든 실패든 응답이 500 ms 근처 안에서 끝난다.
- 장애 전과 장애 후: 각 구간의 예산 안 201 비율이 0.99 이상이고 201 p99가 500 ms 이하다. 장애가 그 40초 밖으로 번지지 않았다는 뜻이다.
- 장애 중 응답을 받지 못한 요청의 주문이 저장되지 않는다. ambiguous outcome 수로 본다.

## 보여 주지 못하는 것

- 연결은 되지만 응답이 아예 오지 않는 장애. 이 scenario의 lookup은 2초 뒤 반드시 응답하므로, 응답 대기 한도에 끝까지 닿는 impl의 모습은 나오지 않는다.
- 지연이 impl의 기한 근처인 경우. 지연이 2초로 크기 때문에, timeout impl이 300 ms를 조금 넘는 정상 응답까지 버리는 비용은 드러나지 않는다.
- 일부 요청만 느려지는 장애와 40초보다 긴 장애.
- 느려진 기능이 다른 기능으로 번지는지. 이 problem의 업무 API는 주문 하나뿐이다.

- Q. lookup 호출에 기한을 두면 장애 중에도 막히지 않나? — 답함 · 20261031-002528-external-api-api-slow-timeout-8def62 (2026-11-13): timeout의 장애 중 k6 요청 timeout은 0건, 201 p99는 293 ms였고, 장애 후 구간의 예산 안 201 비율은 0.994였다(repeat별 구간 값에서 중앙값을 직접 구함).
- Q. 두 impl의 SLO 판정은 다른가? — 답함 · 20261031-004309-external-api-api-slow-naive-2c0c93, 20261031-002528-external-api-api-slow-timeout-8def62 (2026-11-13): 예산 안 201 비율의 run 수준 값은 naive 0.666, timeout 0.665로 거의 같고 둘 다 missed다. measured 전체로 판정하면 두 impl의 차이가 보이지 않고, 차이는 장애 구간의 지연과 k6 timeout에서만 보인다.
- Q. 장애가 끝난 뒤 두 impl은 얼마나 빨리 돌아오나? — 답함 · 20261031-004309-external-api-api-slow-naive-2c0c93, 20261031-002528-external-api-api-slow-timeout-8def62 (2026-11-13): time-to-recovery의 run 수준 값은 naive 991 ms, timeout 995 ms로, 둘 다 회복 조건을 지켰다.
- Q. 장애 중에도 주문 일부를 성공시킬 수 있나? — 열림 · 후보: cache fallback impl, 마지막으로 받은 가격으로 주문을 만든다.
- Q. 장애가 계속되는 동안 매 요청이 lookup을 기다릴 필요가 있나? — 열림 · 후보: circuit breaker impl, 실패가 이어지면 lookup 호출을 잠시 멈춘다.
- Q. 지연이 timeout impl의 기한(300 ms) 근처면 정상 주문을 버리게 되나? — 열림 · 후보: 지연을 300~500 ms로 거는 새 scenario.
