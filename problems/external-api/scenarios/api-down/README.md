# api-down: 외부 상품 API가 40초 동안 죽는다

## 브리핑

### 상황

주문 API가 lookup에 가격을 물으면, lookup 연결이 거부되거나 끊겨 응답을 기다리지 않고 실패한다. 실제 서비스로 치면 외부 상품 API 서버가 내려갔거나 배포 중에 사라진 상황이다.

k6가 초당 50건의 주문을 일정하게 보낸다. 30초 warmup 뒤 120초 동안 측정하고, 측정 시작 40초 뒤부터 80초까지 40초 동안 lookup이 죽는다. k6는 15초 안에 응답을 받지 못한 요청을 끊는다. 이 밖의 설정은 같은 폴더의 [`scenario.yaml`](scenario.yaml)에 있다.

이 장애 유형을 고른 이유는 [api-slow](../api-slow/README.md)와 대비하기 위해서다. 응답이 늦는 api-slow와 달리 여기서는 실패가 바로 드러나므로, 요청이 업무 스레드를 오래 붙잡지 않을 것으로 기대한다. 이 scenario는 외부 API가 죽었을 때 주문 API가 빠르고 정확하게 실패를 알리는지, API가 돌아오면 끊긴 연결을 버리고 바로 정상화되는지를 묻는다.

### 클리어 조건

repeat 하나가 아래를 모두 만족하면 클리어다. 기준은 하네스 판정과 같다([problem README의 요구사항](../../README.md#요구사항)).

- repeat가 complete이고 measurement validity가 valid다.
- SLO: measured 요청 전체 가운데 500 ms 안에 201로 끝난 요청의 비율이 0.99 이상이고, 201의 p99가 500 ms 이하다.
- 회복 조건: 장애 해제를 확인한 뒤 60초 창 안에 예산 안 201이 연속 5번 도착한다.
- 불변 조건: 확인된 위반이 없고 증거가 완전하다. ambiguous outcome은 위반으로 세지 않고 따로 보고된다.

lookup 응답이 있어야만 주문을 만드는 impl로는 이 scenario의 SLO를 클리어할 수 없다. 장애 40초는 measured 120초의 3분의 1이고, 그동안 발행한 요청은 201을 받을 수 없다. 그래서 예산 안 201 비율은 최대 약 0.67로, 0.99에 못 미친다. naive와 timeout은 둘 다 이런 impl이다.

### 보조 목표

하네스가 판정하지 않음. 사람이 리포트의 장애 전·중·후 구간 값을 보고 판단한다.

- 장애 중: 실패가 빨리, 정해진 상태 코드로 돌아온다. k6 요청 timeout이 0건이고, 실패 응답이 500 ms 안에 503으로 끝난다.
- 장애 후: 구간의 예산 안 201 비율이 0.99 이상이고 201 p99가 500 ms 이하다. 끊긴 연결이 남아 장애 뒤까지 실패가 이어지지 않았다는 뜻이다.
- 장애 전: 같은 기준을 만족한다. 이 repeat의 앱이 정상으로 출발했다는 확인이다.

## 보여 주지 못하는 것

- 연결은 되지만 응답이 오지 않는 장애. 이 scenario에서는 연결이 바로 거부되거나 끊기므로, 응답 대기 한도까지 기다리는 impl의 약점이 나오지 않는다. 실제 장애에서는 이쪽이 더 흔할 수 있다.
- 이름 조회(DNS) 실패나, 여러 lookup 인스턴스 중 일부만 죽는 장애.
- 40초보다 긴 장애에서 연결 재시도가 쌓이는 모습.

- Q. lookup이 돌아온 뒤 끊긴 연결 때문에 실패가 이어지지는 않나? — 열림 · 후보: api-down scenario를 naive와 timeout으로 repeat 다섯 개 모두 실행한 run.
- Q. 연결은 되는데 응답이 오지 않으면 naive는 요청마다 10초씩 막히나? — 열림 · 후보: 응답 없음 장애를 거는 새 scenario.
- Q. 죽은 API에 요청마다 연결을 시도할 필요가 있나? — 열림 · 후보: circuit breaker impl, 실패가 이어지면 lookup 호출을 잠시 멈춘다.
