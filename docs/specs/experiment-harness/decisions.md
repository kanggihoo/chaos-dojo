# 실험 하니스 decisions

Glossary: [GLOSSARY.md](../../../GLOSSARY.md) · ADRs: [0001](../../adr/0001-python-uv-tooling-with-schema-contract.md)

## 이 문서를 읽는 법

**무엇을 만드나.** 시즌0의 실험 틀(하니스)이다. A1은 "재고 100개를 두고 주문이 몰리는" 문제(카타)이고, `naive`(일부러 경쟁 버그를 둔 풀이)와 `atomic-update`(조건부 UPDATE 한 문장으로 막는 풀이)가 그 풀이(impl)다. 하니스는 어떤 impl을 붙여도 같은 환경을 빠르게 만들고, 같은 방식으로 부하와 장애를 넣고, 불변식으로 판정하고, 같은 형식의 리포트를 만든다. 용어는 [GLOSSARY.md](../../../GLOSSARY.md)를 따른다.

**한 번의 실행 흐름.** 예측 작성 → 사전 점검 → (시도마다) 스택 생성 → 준비 확인 → 워밍업(성능 시나리오만) → 부하 + 장애 주입 → 드레인 → 불변식 판정 → 기록 → 정리 → 리포트.

**Status 읽는 법.** `settled`는 확정이다. `provisional`은 결정은 확정이지만 그 안의 수치가 잠정값이라는 뜻이다. `Default`에 적힌 값을 지금 그대로 지키고, 적힌 조건(대개 A1 사전 실행)에서 다시 정한다.

**PLAN과의 관계.** 출발점은 [PLAN.md](../../PLAN.md)다. 아래 결정이 PLAN과 다르면 아래가 우선이고, PLAN은 D-1에 따라 고친다.

## D-1 범위
- Status: settled
- Decision: 환경 구성, 실행 루프, 장애 주입, 불변식 판정, 결과 기록, 리포트 생성을 하나의 기능으로 만든다(PLAN 시즌0 1~4주차). 카타 A1과 impl `naive`·`atomic-update`가 첫 사용처다. A1에 필요한 공통 계약만 만들고, 쓰일지 모르는 범용 기능은 미리 만들지 않는다. PLAN.md를 이 문서의 결정과 맞게 고치는 것까지가 완료 조건이다.
  - PLAN에서 고칠 곳: 스택 표, k6 실행 방식, 이미지 고정, 시즌0 주차표(Makefile, Rust 리포트), DoD 명령(실제 `uv run` 명령 + 예측 준비 단계), 시즌1 Rust 오케스트레이터 문장(나중의 학습용 이행으로), 디렉터리 예시, I3 정의(D-7), 측정 신뢰도 규칙, 관측·자원 설명(D-5, D-17), 공정성 기록(D-18), 예측과 AI 도움(D-16), 결과 구조(D-13), 리포트 구성(D-15), 지원 호스트와 자체 검증(D-3, D-19).
  - PLAN에서 낮추지 않는 것: 백엔드 실험 우선, 자원 한도, 계측 오버헤드 +10% 경고, 튜닝 예산 3사이클, 발견 승격 조건, 도구 작업 30% 규칙.
- Rejected: 리포트 생성기를 다음 기능으로 분리 → 사용자가 통일된 리포트를 이 틀의 일부로 요구했다
- Reuse: `docs/PLAN.md#DoD` (modify) — 위 목록의 문장을 이 문서의 결정과 일치시키고, 낮추지 않는 것 목록은 그대로 둔다

## D-2 백엔드 스택 (시즌0 impl)
- Status: settled
- Decision: Java 21 + Spring Boot 4.1 MVC + JdbcTemplate/JdbcClient + HikariCP, 플랫폼 스레드. 두 impl은 같은 설정·트랜잭션 범위·응답 의미를 쓰고 재고 차감 방식만 다르다. naive는 읽은 값으로 계산해 쓰고, atomic-update는 `stock > 0` 조건부 UPDATE 결과로 확정한다. 앱이 1코어/512MB에 맞는지(전체 프로세스 메모리, 기동부터 준비 완료까지의 시간, 워밍업 수렴 시간)를 먼저 실측한다.
  - 실측에서 한도를 못 맞추면 한도를 몰래 늘리거나 튜닝에 시간을 쓰지 않고 Go(net/http + pgx)를 다시 검토한다.
  - Java 21 → 25 전환 비교는 이후 카타 후보로 남기며 이 기능의 범위가 아니다.
- Rejected: JPA/Hibernate → 실험에 집중하려면 SQL이 코드에 그대로 보여야 락·트랜잭션을 추적하고 AI 코드를 리뷰하기 쉽다 · Java 25 → 사용자가 21로 시작하고 25 비교를 나중 카타로 두기로 했다 · Spring Boot 3.x → 3.5의 오픈소스 지원이 2026-06-30에 끝났다

## D-3 도구 언어와 실행 환경
- Status: settled
- Decision: 실행기(오케스트레이터)와 리포트 생성기 모두 Python으로 만들고 uv로 관리한다. Windows 11(PowerShell)과 macOS(zsh)에 Docker Desktop과 uv만 설치하면 같은 `uv run` 명령으로 돈다. make, WSL 배포판, Git Bash는 필요 없다. 나중에 Rust 학습 목적으로 이행하며, 그때도 D-14의 계약과 시험을 그대로 통과해야 한다.
  - 고정: Python patch 버전은 `.python-version`, 의존성은 버전 관리하는 `uv.lock`, uv 자체 버전은 `required-version`으로 고정한다. 정식 실행은 `uv run --locked --exact`로 한다(lock을 바꾸지 않고, 고정된 의존성과 정확히 같은 환경에서만 실행). 사전 점검은 인터프리터·uv·의존성·소스가 맞지 않으면 실행을 거부한다. 설치와 동기화는 측정 구간 밖에서 한다.
  - 셸별로 업무 로직을 따로 두지 않는다. 경로, 하위 프로세스, 중단 시 정리는 Python 안에서 처리한다.
  - k6는 호스트에 설치하지 않고 버전을 고정한 컨테이너로 실행한다.
- ADR: [0001](../../adr/0001-python-uv-tooling-with-schema-contract.md)

## D-4 impl 연결 계약
- Status: settled
- Decision: impl은 컨테이너 단위로 붙는다. impl은 Dockerfile, 준비 완료 신호, 진행 중 업무 작업 수, PROVENANCE.md를 제공하고, 네트워크·자원·DB 접속·타임아웃은 하니스가 주입한다. 모든 실행 전에 `check`가 계약을 검사한다. 새 impl·카타는 기존 예제를 복제하고 식별자만 바꾸는 명령으로 만든다. (manifest = impl이나 카타의 구성을 설명하는 설정 파일)
  - 준비 완료 판정: impl 신호 + 하니스 확인. 하니스는 DDL(테이블·인덱스 정의 SQL)과 seed 데이터(초기 데이터)가 적용됐는지, 앱이 실제로 어느 DB에 붙었는지 확인한다. 풀 최대값 10은 HikariCP에 실제로 적용된 설정으로 확인하고, 격리 수준 READ COMMITTED는 앱이 빌린 DB 연결에서 확인한다. 지금 열려 있는 연결 개수만으로는 풀 최대값을 증명하지 않는다. 측정 대상이 아닌 상품에 읽기 전용 smoke 요청을 1회 보낸다. 60초 안에 확인되지 않으면 시도를 "not ready"로 중단한다.
  - 진행 중 업무 작업 수는 DB 커밋·롤백과 작업 종료까지 포함한다. A1에는 응답 뒤에 따로 실행되는 업무가 없다.
  - PROVENANCE.md 필수 항목: 생성 모델과 버전(공개되지 않았으면 unknown과 이유), 요구사항 프롬프트 원문 또는 보존 위치, 수동 수정 이력(없으면 없다고 명시). 빠지거나 placeholder면 `check`가 거부한다.
  - `new-impl` / `new-kata`: 명시적으로 고른 기존 예제를 새 위치에 복사하고 manifest 식별자와 선언된 실행 참조만 바꾼 뒤 `check`를 돌린다. 기존 대상은 덮어쓰지 않는다. 빌드 산출물·결과·실행 상태는 복사하지 않는다. PROVENANCE에 원본 경로·커밋을 남기고 새 수정 이력을 시작한다. 의존성(impl)과 DDL·seed·부하·판정(카타)은 출처와 함께 상속하며, 일괄 초기화나 소스 전체 문자열 치환은 하지 않는다.
  - `check`는 식별자 충돌, manifest·파일 참조, 지원 버전, 의존성 계약을 검사하고, 확인할 수 없는 참조를 통과시키지 않는다. `check` 통과가 준비·정합성·성능의 통과를 뜻하지는 않는다.
- Rejected: impl이 compose 조각을 직접 제공 → impl이 고정 조건을 덮어쓸 수 있다 · 공유 코드베이스 안의 모듈로 교체 → 스택에 묶인다 · 언어별 템플릿 라이브러리 → 스택이 하나뿐인 지금은 빈 틀만 늘어난다

## D-5 의존성과 자원 예산
- Status: provisional
- Decision: 앱은 1코어/512MB이고, 앱 안에서 도는 OTel agent의 비용도 여기에 포함한다. impl이 쓰는 인프라 의존성(PostgreSQL, 이후 Redis 등)은 합계 1코어/1GB 안에서 하니스가 배분한다. Toxiproxy, k6, OTel Collector, Prometheus, Grafana, cAdvisor는 이 두 예산 밖에서 각자 고정 한도를 갖고 사용량을 기록한다. impl은 의존성을 이름으로만 선언하고, 버전·설정·자원은 하니스 카탈로그가 정한다.
  - 지금 카탈로그에는 PostgreSQL만 둔다. Redis·Kafka는 실제로 필요한 카타가 올 때 추가한다.
  - 의존성 추가는 선언된 변수다. 런 셋 meta에 impl별 의존성, 컨테이너 수와 역할, 자원 배분, 늘어난 네트워크 경유·장애 지점을 선언으로 적고, 시도마다 실제 컨테이너와 CPU·메모리 사용량을 실측으로 적는다. 리포트는 선언과 실측을 구분해 구현 차이 구획에 보여 준다.
  - "k6 CPU > 70%"의 분모는 k6에 할당한 CPU다. 측정 구간의 1초 관측 중 하나라도 넘으면 시도가 무효다.
  - 장애 도구나 관측 도구의 자원을 바꾸면 새 런 셋으로 비교한다. Toxiproxy가 병목이 되지 않는지 사전 점검한다.
- Default: k6 2코어/1GB. Toxiproxy·Collector 한도와 PostgreSQL 배분은 착수 시 실측으로 정한다. 사전 점검에서 부족하면 모든 impl에 같은 값으로 바꾼 새 런 셋에서 다시 정한다.
- Rejected: Toxiproxy를 인프라 예산에 포함 → 의존성을 추가할 때마다 예산이 다시 나뉘어 장애 도구 비용이 연구 변수와 섞인다 · 모든 의존성을 항상 실행 → 쓰지 않는 서비스가 비교 조건을 바꾼다

## D-6 환경 고정과 환경 지문
- Status: settled
- Decision: 고정 이미지(PostgreSQL, Toxiproxy, k6, Prometheus, cAdvisor, OTel Collector, Grafana)는 정확한 patch 버전과 multi-arch index digest(이미지 내용을 식별하는 hash)로 한곳에 적고, Compose는 그 값만 읽는다. OTel Java agent JAR도 정확한 버전과 내용 hash로 고정하고 실제로 로딩된 파일을 확인한다. 시도마다 환경 지문을 만든다. 고정 조건이 다르면 실행 전에 막고, 실행 뒤 발견하면 그 시도를 이유와 함께 제외한다.
  - 지문에 들어가는 것: 하니스 커밋(작업 트리가 더러우면 거부하거나 diff hash 포함), 카타 명세 버전, 워크로드·장애 타임라인·DDL/seed/복원 절차의 내용 hash, 저장 매체, DB 설정, 관측·워밍업 규칙, 실제 이미지 digest와 플랫폼, OTel agent 버전·hash·설정 hash, Collector·Grafana 설정 hash, Docker VM 자원과 엔진 버전, 호스트 OS·아키텍처, Python·uv 버전과 lock hash, 부하 순서의 random seed.
  - 허용되는 차이(선언된 변수): impl 간 코드·이미지와 명시한 의존성 차이, 그리고 D-17 짝 비교에서의 계측 on/off뿐이다. 같은 impl의 반복끼리는 이 값들도 같아야 한다. 호스트가 다른 결과는 어떤 경우에도 한 런 셋에서 합치거나 비교하지 않는다.
  - 사전 점검은 고정값과 렌더링된 Compose 설정, 실제 실행 이미지를 비교하고, 셸 변수나 override로 바뀐 고정값을 거부한다. 필요한 플랫폼의 이미지가 없으면 태그나 에뮬레이션으로 대신하지 않고 실행 불가로 알린다.
  - DB 저장소: 시도마다 새 named volume을 만든다. 판정 증거와 진단을 수집한 뒤 그 시도가 만든 볼륨을 제거하고, 제거에 실패한 상태를 다음 시도에 쓰지 않는다. tmpfs는 카타가 명시할 때만 쓰며, 저장 매체가 다른 반복은 섞지 않는다.
- Rejected: 기본 저장소를 tmpfs로 고정 → A1이 I/O 영향을 받지 않는다는 근거가 없다 · 지문 불일치를 경고만 → 다른 환경의 결과가 조용히 섞인다

## D-7 카타 계약 (A1)
- Status: provisional
- Decision: 카타가 API 계약, DDL·인덱스·seed 데이터·복원 절차, 워크로드, 장애 타임라인, 판정 SQL, 메타데이터를 소유한다. API는 OpenAPI로 메서드·경로·요청/응답 스키마·상태코드표를 고정하고, 오류 본문은 RFC 9457(problem+json)을 따른다. A1은 수량 1 주문 생성과 재고 조회를 고정하고, 주문 확정·음수 원장 행·재고 변경을 한 트랜잭션에 쓴다. 워크로드는 k6 constant-arrival-rate(초당 도착 수를 고정하는 open model)만 허용한다.
  - 스키마 소유: 하니스가 준비용 계정으로 앱 시작 전에 DDL과 seed 데이터를 적용한다. 앱 DB 계정에는 DDL 권한이 없고, 앱의 자동 migration은 끈다. 시도 전후로 테이블·인덱스를 카타 DDL과 대조해 차이를 기록한다. 스키마를 실험 변수로 삼으려면 카타 계약부터 바꾼다.
  - 상태코드: 확정 201, 품절 409, 잘못된 요청 400, DB 접속 불가·시간 초과 503, 그 밖의 내부 오류 500. DB 오류를 품절로 바꾸지 않는다. 품절 거절은 주문·원장·재고 변경을 남기지 않는다.
  - 시즌0은 impl과 k6 모두 업무 요청 재시도를 하지 않으며, 드라이버의 숨은 재시도도 확인한다. 타임아웃은 카타가 고정하고 하니스가 주입하며, 앱이 실제로 적용했는지 증거로 확인한다. 타임아웃이나 503이 "DB에 반영되지 않았다"는 증거라고 가정하지 않는다(판정은 드레인 뒤 DB로 한다).
  - I3(상품별): 재고 ≥ 0, 확정 주문 수량 합 = −원장 변동 합, 현재 재고 = seed 재고 + 원장 변동 합. 세 번째 절이 있어야 "주문과 원장은 맞는데 재고 차감만 사라진" lost update를 잡는다.
  - A1-correct: 측정 상품 1개, 재고 100, 수요 100 초과. A1-perf: 재고가 워밍업과 측정 부하를 모두 감당하고, 요청을 상품 1/10/100개에 균등 분산하는 부하 조건 셋을 따로 둔다. 분산 순서는 random seed와 요청 순번으로 정해 impl 속도에 따라 바뀌지 않게 한다.
  - `check`는 constant-arrival-rate 외의 executor를 거부하고, 실행 때 실제 k6 설정과 대조한다.
  - 카타 메타데이터: 성공 조건, 재현 명령, 자원 상한, 명세 버전, 난이도, 예상 소요(학습·풀이 시간이며 부하 시간과 다름)에는 유효한 값이 필수다. 선행 지식과 알려진 한계는 없을 때만 명시적인 "없음"이나 빈 목록을 쓴다. TODO나 placeholder는 통과하지 않는다.
- Default: DB 새 연결 획득 1초, 풀 획득 1초, statement 2초, 앱 요청 전체 기한 4초, k6 요청 5초. A1 사전 실행으로 확인한 뒤 카타에 고정하며, 결과를 본 뒤에는 바꾸지 않는다.
- Rejected: impl마다 migration을 두고 결과 스키마를 비교 → 스키마가 숨은 변수가 된다 · 원장 없이 재고만 비교 → PLAN의 원장 계약이 사라진다 · 판정기가 원장을 만듦 → 독립 증거가 줄어든다

## D-8 장애 타임라인
- Status: provisional
- Decision: 카타 파일이 "부하 시작 10초 뒤 DB에 지연 200ms를 넣는다"처럼 오프셋·동작·대상·매개변수를 선언한다. 하나의 공통 실행기가 Toxiproxy와 docker pause/kill을 모두 다룬다. 기준점은 k6가 알려 준 측정 시나리오의 실제 시작 시각이며, 프로세스를 띄운 시각이나 로그가 도착한 시각이 아니다. 예정보다 일찍 실행하지 않는다. 지킬 수 없게 된 장애는 시도를 무효로 만든다. 시즌0은 DB 지연 1종만 구현한다.
  - 두 가지 시계를 쓴다. 기록에는 모두가 비교할 수 있는 공통 기준 시각(epoch)을 쓰고, 실행 예약에는 시스템 시각 보정에도 거꾸로 흐르지 않는 단조 시계를 쓴다. 두 시계의 대응 오차도 기록한다.
  - events.jsonl에 계획 시각, 명령 시작 시각, 성공 확인 시각, 결과, 오류를 남긴다.
  - 주입이 실패·시간 초과·중단되면 진단을 보존하고 그 측정을 제외하며, 다음 시도 전에 장애를 반드시 해제한다.
  - 허용치는 하니스 기본값이 있고 카타가 다른 값을 정할 수 있다. 정한 값은 모든 impl과 반복에 같게 적용하고 지문에 넣는다. 결과를 본 뒤 완화하지 않는다.
- Default: 시작 신호 도착은 k6 시작 시각 후 1초 이내, 주입 성공 확인은 예정 시각 후 500ms 이내, 시계 대응 오차는 100ms 이내. A1 사전 실행에서 확인한다.
- Rejected: k6 스크립트 안에서 Toxiproxy를 호출 → docker pause/kill을 다룰 수 없고 실패 처리 계약이 갈라진다

## D-9 시도 진행: 초기화, 워밍업, 드레인, 순서
- Status: provisional
- Decision: 시도마다 앱·DB·선언된 의존성·장애 상태를 새로 만들고 같은 seed 데이터를 적용한다. 정합성 시나리오는 워밍업 없이 준비 확인 후 바로 시작한다. 성능 시나리오는 안정화 워밍업 → 드레인 → 업무 데이터 복원·확인 → 측정 순서다. 부하가 끝나면 드레인을 확인한다. impl은 동시에 돌리지 않고 라운드마다 교대하며, impl마다 유효 반복 5회를 목표로 시도 상한 10회를 둔다.
  - 재생성이 호스트 캐시까지 비운다고 주장하지 않는다. 준비 절차와 캐시 조건을 meta에 적는다.
  - 워밍업 안정화 기준은 하니스 기본값이 있고 카타가 정할 수 있다. 처리량 0, 성공 없음, 지표 누락은 안정으로 치지 않는다. 최대 시간 안에 안정되지 않으면 "warmup not stabilised"로 무효다. 정합성 시나리오의 지연 지표는 진단용이며 성능 결과와 집계하지 않는다.
  - 드레인 완료 조건: 새 업무 요청이 없는 상태에서 앱이 보고하는 진행 중 업무 작업이 0이고, 앱 DB 계정에 active 쿼리와 열린 트랜잭션(idle in transaction 포함)이 없는 것이 1초 간격으로 두 번 연속 확인된다. 시간을 넘기면 "drain timeout"으로 무효이며, 그때 얻은 판정은 진단으로만 남긴다. 복원은 드레인 성공 뒤에만 하고, 실패하면 증거를 모은 뒤 스택을 정리한다.
  - 순서와 상한: 라운드마다 시작 impl을 번갈아 바꾸고 순서를 기록한다. 중단·무효 시도도 상한에 세고 모두 보존한다. 유효한 불변식 위반과 버그 미노출도 유효 반복이며, 결과가 마음에 들지 않는다고 바꾸지 않는다. 상한까지 5회를 못 채우면 런 셋은 incomplete다. 시작했거나 중단된 런 셋은 이어 하지 않는다.
- Default: 워밍업은 겹치지 않는 10초 창 3개에서 성공 처리량과 성공 p99가 세 창 중앙값의 ±10% 이내일 때 안정으로 본다. 창마다 성공 표본이 1,000개 미만이면 p99 안정 판정에 쓰지 않는다. 최대 180초. 드레인 최대 30초. A1 사전 실행에서 확인한다.
- Rejected: 컨테이너를 유지한 채 TRUNCATE로 초기화 → 반복이 독립이 아니다 · 모든 시나리오에 워밍업 후 복원 → 정합성 판정이 복원 절차의 버그에 기대게 된다 · impl별로 몰아서 반복 → 시간대 잡음이 한 impl에 쏠린다

## D-10 상태와 종료 코드
- Status: settled
- Decision: 시도마다 실행(완료/중단+이유), 측정 유효성(유효/무효+이유들), 불변식 판정(불변식별 통과/위반/미수렴/미평가)을 독립된 세 축으로 기록하고 단계·이유·시각·근거를 붙인다. 불변식 위반은 무효 사유가 아니다. 증거가 없으면 유효로 치지 않는다. 실행 명령은 실행 중단, 필수 산출물 누락, 측정 무효, 리포트 생성 실패일 때 0이 아닌 코드로 끝나고, 정상 수집된 불변식 위반만 있으면 0으로 끝난다.
  - 무효 사유: 부하기 포화(`dropped_iterations > 0` 또는 k6 CPU 초과), 스크레이프 누락, 장애 주입 실패, 워밍업 미안정, 드레인 시간 초과, 지문 불일치, 필수 진단 누락 등.
  - 스크레이프: 필수 대상(cAdvisor, k6 CPU 등)을 1초 간격으로 수집하고, 2구간은 늦게 도착하는 값을 기다리는 유예로만 쓴다. 최종 확인에서 예정된 표본이 하나라도 없으면 무효다. 엔드포인트가 살아 있는 것과 새 값이 도착하는 것을 구분한다.
  - 실패해도 정리, 진단 수집, 가능한 리포트 생성을 먼저 시도한 뒤 종료한다. 명령의 종료 코드와 런 셋의 5회 완결 여부는 따로 기록한다.
- Rejected: 단일 상태값 → naive의 의도된 위반과 하니스 고장이 섞인다 · 측정 무효도 0으로 종료 → 호출 쪽이 무효 결과를 정상으로 이어 처리한다

## D-11 불변식 판정과 판정기 검증
- Status: settled
- Decision: 판정기는 DB를 읽기만 한다. 판정 SQL은 고정된 DB fixture(기대 결과를 아는 시험 입력)로 impl과 무관하게 먼저 검증한다: 정상 상태, I3 각 절을 하나씩 위반한 상태, "주문과 원장은 일치하는데 재고 차감만 사라진 상태". 실제 실행에서는 같은 부하·장애로 두 impl을 돌리고 naive의 버그 노출 횟수/유효 반복 수를 기록한다. 장애 복구 시각부터 60초 경계까지 적용 대상 불변식을 1초마다 평가한다.
  - A1에서는 I3만 적용하고 I1·I2·I4는 미적용으로 표시한다.
  - 수렴 시간은 복구 후 통과가 처음 관측될 때까지의 시간이다. 그 뒤에 관측된 위반과 드레인 뒤의 최종 판정은 따로 보존하며, 첫 통과만으로 전체 통과를 확정하지 않는다. 60초까지 통과가 관측되지 않으면 미수렴(실패)이다.
  - naive의 위반 없는 반복은 판정 통과 + "bug not exposed"로 기록한다. atomic-update의 위반은 판정 실패다. naive의 위반 증거가 하나도 없으면 DoD 미충족이며, 노출될 때까지 무제한 재실행하지 않는다.
  - 노출을 높이는 부하는 사전 점검에서 정하고 결과 수집 전에 고정한다. naive에만 다른 조건을 주지 않는다.
  - 조회할 수 없었던 것을 데이터 위반으로 표현하지 않고 미평가와 이유로 남긴다. 관측하지 못한 수렴 시간은 0이 아니다.
- Rejected: 모든 반복에서 naive 위반을 보장하도록 조율 → 경쟁은 비결정적이라 보장할 수 없고, 노출 여부로 반복을 고르면 결과가 편향된다

## D-12 통계 정의
- Status: provisional
- Decision: 집계 대상은 측정 구간 [시작, 끝) 안에서 시작된 업무 HTTP 요청이다(워밍업·준비·판정 요청 제외, 구간 뒤에 도착한 응답은 포함). 예를 들어 시도 1회 안에 요청 시도 1,000개가 들어간다. 오류율 = 오류/요청 시도 수, 주 처리량 = 성공/측정 초, 보조 처리량 = (성공+비즈니스 거절)/측정 초. 접속 실패와 타임아웃은 오류다. p99는 결과 유형별 원시 표본으로 계산한다. impl별 집계는 유효 반복의 중앙값과 CV다.
  - p99: 요청 지연을 짧은 순으로 정렬했을 때 99% 지점의 값. 정렬한 n개 중 ceil(0.99n)번째 값이며, 여기서 n은 그 결과 유형의 요청 표본 수다. 표본이 최소 수에 못 미치면 null(insufficient_samples).
  - CV: 반복 측정값의 표준편차(n−1)를 평균으로 나눈 상대 변동 크기(0.1 = 10%). 여기서 n은 그 지표값이 있는 반복 수다. n<2이거나 평균이 0이면 null과 이유를 남기며, null은 안정이 아니다. CV가 10%를 넘으면 "unstable: rerun / investigate"로 표시하되 반복을 빼지 않고, 다시 돌릴 때는 새 런 셋으로 원본과 함께 보존한다.
  - 지표마다 값이 있는 유효 반복만 골라 중앙값과 CV를 같은 집합으로 계산한다. 다른 지표가 null이라는 이유로 반복 전체를 버리지 않는다. 지표별 유효/전체 반복 수와 제외 이유를 표시하며, 5회 미만을 5회 집계처럼 보이지 않는다.
  - 완결된 집계에서는 요청 시도 수 = 성공 + 거절 + 오류다. 중단된 시도에서는 결과가 없는 요청을 unresolved로 따로 남긴다. 요청 시도 수 0이나 측정 구간 0은 유효한 측정이 아니다. `dropped_iterations`는 요청 시도 수에 넣지 않고 시도 자체를 무효로 만든다.
  - null과 0을 스키마에서 구분하고 서로 바꾸지 않는다.
- Default: p99 최소 표본 1,000개. 사전 점검 뒤 모든 impl에 같게 고정한다.
- Rejected: Prometheus 히스토그램 버킷으로 p99 계산 → 꼬리 지연 차이가 버킷에 묻힌다 · 품절 거절을 주 처리량에 포함 → 빠른 거절이 처리 능력처럼 보인다

## D-13 결과 디렉터리와 보관
- Status: provisional
- Decision: 런 셋마다 고유 디렉터리 하나를 두고, 그 안에 런 셋 meta(시나리오, 부하 조건, 고정 환경, 선언된 변수, 대상 impl, 동결된 예측)와 impl×시도 하위 디렉터리(실제 환경, 상태, metrics.json, events.jsonl, 진단)를 둔다. 날짜만으로 식별하지 않고 덮어쓰지 않는다. 실패·제외된 시도도 남긴다. git에는 meta, 모든 시도의 metrics·events·상태, 사용자 notes, arch, 리포트, 한도 안의 SQL 진단을 올린다. Prometheus TSDB와 큰 로그는 로컬에만 두고 위치·크기·hash·잘림 여부를 meta에 적는다.
  - 핵심 위반 증거와 필수 meta·metrics·events는 크기 한도 때문에 버리지 않는다.
- Default: 진단·로그 파일당 1MiB, 시도당 텍스트 합계 10MiB.
- Rejected: PLAN의 날짜×카타×impl 디렉터리 유지 + 목록 파일로 연결 → 한 비교가 여러 디렉터리에 흩어지고 목록 파일이 두 번째 진실이 된다

## D-14 계약 파일 형식
- Status: settled
- Decision: 카타 manifest, impl manifest, 런 셋 meta, 예측, metrics, events(행 단위)의 정식 계약은 언어와 무관한 JSON Schema(Draft 2020-12, 참조는 저장소 안에 둠)이며 schema_version을 갖는다. 모르는 버전은 거부한다. Python 코드의 내부 구조는 계약이 아니다. 나중에 Rust로 옮길 때도 같은 스키마, fixture, golden 리포트(기대 출력 파일), 경계 시험을 통과해야 한다.
  - schema_version(파일 형식 버전)과 카타 명세 버전(실험 의미 버전)은 다른 것이다.
  - YAML은 JSON으로 표현 가능한 값으로 읽어 같은 스키마로 검증한다. 중복 키, 언어 전용 태그, 유한하지 않은 숫자는 거부한다.
  - 준비 중·시작됨·부분 결과 상태마다 필수 필드를 따로 정해, 예측 준비나 부분 리포트가 막히지 않게 한다.
  - 스키마로 표현할 수 없는 의미 규칙(합계, 예측 hash, 환경 일치, CV·p99 계산)은 언어 중립 설명과 정상/오류 fixture의 기대 결과로 고정한다.
- ADR: [0001](../../adr/0001-python-uv-tooling-with-schema-contract.md)

## D-15 리포트
- Status: settled
- Decision: 리포트 한 장은 런 셋 하나를 보여 준다. JavaScript와 외부 요청이 없는 단일 HTML에 SVG 차트를 넣고, 같은 입력이면 바이트까지 같은 결과를 낸다. 지원하지 않는 schema_version은 거부하고, 부분·무효 런 셋은 그 상태를 표시해 그린다. 모든 리포트에 "이 구현·이 튜닝 예산·이 환경에서의 상대 비교"라는 범위 문구를 넣는다. 사용자 해설이나 한 줄 결론이 없으면 draft다.
  - 구성(읽는 순서대로 여섯 묶음):
    1. 질문과 가설: 시나리오의 질문, 동결된 예측의 근거(출처 표시)
    2. 실험 조건: 환경·도구·이미지·플랫폼 버전, 자원 한도, 부하 조건, 장애 타임라인(계획/명령/실제/결과)
    3. 비교 대상과 비용: 구현 차이(manifest·선언된 변수·수동 arch 기반), 앱/인프라/장애 도구/관측 사용량 분리
    4. 관측 결과: 처리량·오류율·결과 유형별 p99·수렴 시간 차트, 불변식 판정, 반복 수와 CV, 예측 평가(D-16)
    5. 사용자 해석: notes와 한 줄 결론
    6. 재현과 원본: 실제 `uv run` 재현 절차(예측 준비 단계 포함), 원본 파일 상대 링크
  - 선언, 검증, 실측, 사용자 해설을 구분해 표시한다. 미평가·표본 없음·미수렴을 0으로 그리지 않는다. 성능 집계는 유효 반복만 쓰고, 제외된 시도와 불변식 위반도 보이게 한다.
  - 출력 결정성: 정렬, 숫자·시간 형식, SVG id를 고정하고 생성 시각, 난수, 호스트 절대 경로를 넣지 않는다. UTF-8, LF.
  - draft 표시: notes가 없거나 비어 있으면 "draft: notes missing", 한 줄 결론이 없거나 placeholder면 "draft: conclusion missing". 하니스는 해설과 결론 내용을 쓰지 않는다. 해설이 채워져도 incomplete·무효·미평가·예측 변경 표시는 남는다.
  - 로컬 결과는 상대 비교로만 표기한다. 부하기와 SUT를 분리한 2VM 재현은 이 기능 범위 밖의 후속 검증이다.
  - 재현 절차로 기존 런 셋을 이어 하거나 덮어쓰는 명령을 내보내지 않는다.
- Rejected: impl별 리포트를 따로 만들고 비교는 사람이 → 핵심 비교를 손으로 하게 된다 · JavaScript 차트 → 재생성마다 결과가 달라질 수 있고 오프라인 보관이 어렵다

## D-16 예측
- Status: provisional
- Decision: 예외 없이 예측이 있어야 런 셋이 시작된다. 하니스가 시작 전 런 셋의 meta와 예측 양식을 만들고 멈추면, 사용자가 채운 뒤 같은 런 셋으로 다시 실행한다(이어 하기가 아니라 시작 전 준비다). 시작 순간 예측 원본을 보존하고 정규화한 hash를 기록에 묶는다. 이후 수정은 감지해 리포트에 표시하고, 적중 평가는 동결본으로만 한다. AI 도움은 허용하되 최종 예측과 근거는 사용자가 책임지고, `ai_assisted` 여부와 도움 범위를 기록한다.
  - 시작 전 검사: 필수 값의 존재·타입·범위, 비교 대상 impl과의 일치, 근거. 비었거나 placeholder면 시작하지 않는다. 해당 없는 필드(단일 impl, 정합성 시나리오의 p99 등)는 명시적인 not_applicable과 이유로 적는다.
  - 예측 평가(리포트마다): 승자 적중, 순위 점수(미리 정한 비교 쌍 중 순서가 맞은 비율), impl별 p99 범위 포함 여부(유효 반복 중앙 p99가 예측 구간 안인지), ai_assisted. 승자·순위의 기준 지표와 동률 규칙은 결과를 보기 전에 카타에 정한다. 해당 없음과 평가 불충분은 맞음/틀림에 넣지 않는다.
  - 적중 요약 페이지: 모든 런 셋을 모은 정적 페이지 1장이 적중 추이를 ai_assisted 여부별로 나눠 보여 준다. 집단마다 서로 다른 카타 수, 평가 가능한 런 셋 수, 반복 수, 제외 이유를 표시한다. 고정된 기준에 못 미치면 "탐색 지표"로 표시한다. 반복 5개를 예측 5개로 세지 않고, 리포트 재생성을 새 예측으로 세지 않으며, 다른 환경의 성능값을 합산하지 않는다.
  - 블라인드 카타는 제출·공개 전 AI 도움을 금지한다(블라인드 카타 자체는 이 기능 범위 밖).
  - 하니스 자체 검증(D-19)은 런 셋이 아니라 예측이 필요 없다. 실제 실험을 자체 검증으로 이름만 바꿔 우회할 수 없다.
- Default: "탐색 지표" 기준은 서로 다른 카타 10개 미만. 시즌이 끝날 때 다시 본다.
- Rejected: 디버그 실행은 예측 없이 허용 → 사용자가 예외 없는 강제를 골랐다 · AI 도움 금지 → 사용자가 개념 공부와 수치 논의 모두 허용하기로 했다 · 예측을 명령 인자로 받기 → 근거를 적기 어렵고 보존이 어긋난다

## D-17 관측과 계측
- Status: provisional
- Decision: 앱에 OTel Java agent를 붙여(기본 on) 메트릭을 수집하고 Grafana로 본다. 트레이스·로그 export는 끄며, Tempo·Loki는 PLAN의 진입 조건까지 미룬다. 시즌0에서 atomic-update × A1-perf 한 조건으로 agent on/off 짝 런 셋을 한 번 돌려, p99 오버헤드가 +10%를 넘으면 경고한다. 시도마다 SQL 진단을 자동 수집한다.
  - **지표 수집 경로.** agent는 앱 안에서 측정하고, OTel Collector는 받은 지표를 전달하고, Prometheus는 지표를 저장하고, Grafana는 조회 화면이다(Grafana는 저장하지 않는다). 미리 구성한 대시보드: HTTP 서버 지연·오류, Hikari 활성/대기/획득 지연, JVM heap·GC·스레드, cAdvisor 자원. 실시간 디버깅용이며, 리포트는 결과 파일로 만든다(D-15). Grafana의 서버 p99를 k6의 p99와 혼동하지 않는다. 내보내기(export)·수집 주기는 1초 관측에 맞추고, 수집 성공만으로 원천 지표가 최신이라고 보지 않는다. 고정 agent 버전에서 실제로 나오는 지표 이름·단위를 사전 점검에서 확인하고, Micrometer와 중복 집계하지 않는다.
  - **계측 비용 비교(짝 런 셋).** 같은 이미지·JDK·스레드·풀·타임아웃·자원·부하·장애·저장 매체에서 agent 로딩 여부만 다르다. on과 off 각각 유효 5회, 시작 시도 최대 10회, 교대 실행, 같은 무효 규칙을 적용한다. 오버헤드 = (on의 중앙 p99 / off의 중앙 p99 − 1) × 100%이고, p99는 k6 원시 성공 표본으로 계산한다. off의 중앙 p99가 0이거나 표본·반복이 부족하면 "평가 불충분"이다. off 쪽에서 agent 지표가 없는 것은 예상된 상태이며 스크레이프 누락이 아니다. cAdvisor, 준비·진행 작업 수·드레인 검증은 양쪽 모두 유지한다. 나머지 런 셋은 agent on으로 고정하고 이 결과를 조건과 함께 참조하며, 다른 조건으로 일반화하거나 p99에서 빼서 보정하지 않는다. 짝 런 셋도 예측이 필요하다.
  - **SQL 진단.** 측정 부하 직전에 pg_stat_statements를 초기화하고 그 시각을 기록하며, 부하·드레인이 끝날 때 덤프한다. 측정 내내 1초 간격으로 락·활동 스냅샷을 찍는다. 총 실행 시간 상위 SQL을 판정 증거를 보존한 뒤 EXPLAIN(ANALYZE 없이, 고정 대표 SQL·파라미터나 generic plan)하고 사후 계획임을 표시한다. 수집 계정은 앱 계정과 분리한다. 수집 실패는 필수 진단 누락이며 판정을 바꾸지 않는다.
- Default: 짝 런 셋은 상품 10개 부하 조건. EXPLAIN 대상은 상위 5개. 사전 점검에서 확인한다.
- Rejected: 이번 범위에서 OTel 제외 → 사용자가 지표 읽는 안목을 기르기 위해 포함을 골랐다 · 트레이스를 지금 Tempo에 저장 → PLAN이 실제 설명 공백이 보일 때 추가하기로 했다

## D-18 공정성 체크리스트 기록
- Status: settled
- Decision: PLAN의 공정성 항목(스키마, 격리 수준, 요청 의미, 재시도 정책, 커넥션 풀, 타임아웃, 트랜잭션 범위, 인덱스)을 시도마다 빠짐없이 기록하고, 항목마다 확인 범위·증거·확인 주체를 남긴다. 하니스가 관측할 수 있는 항목은 검증한다. 불일치나 필수 증거 누락은 실행 전에 막고, 실행 뒤 발견하면 제외한다.
  - 풀·격리 수준·타임아웃은 주입했다는 사실만으로 검증으로 치지 않고, 앱의 실제 설정 증거(D-4)를 요구한다.
  - 요청 의미·재시도·트랜잭션 범위: manifest 선언만 있으면 "declared, not verified"로 표시한다. 동작 검사나 코드 리뷰로 확인한 부분이 있으면 확인 방법·범위·근거를 함께 표시하되, 일부 확인을 전체 의미의 증명으로 확대하지 않는다.
  - impl을 고정(태그)할 때 사용자가 diff를 한 번 리뷰하고 notes에 "이 구현의 약점"을 적는다. 이후 시도는 그 리뷰한 커밋과 일치하는지 연결한다.
- Rejected: 모든 항목을 선언만 → 검증하지 않은 공정성이 통과처럼 보인다

## D-19 하니스 자체 검증
- Status: settled
- Decision: 명령 하나로 격리된 실제 컨테이너에서 하니스의 경계 동작을 검증한다. Windows와 macOS 양쪽에서 통과해야 한다(macOS도 best-effort가 아니다). 리포트 생성기는 고정 결과 fixture와 golden 출력으로 따로 검증한다. 검증 대상은 경계에서 보이는 상태·증거·종료 결과이며, 내부 구현을 그대로 되풀이하는 시험이 아니다.
  - 컨테이너 검증 항목: atomic-update의 I3 통과, naive의 위반 증거(고정 부하, 유한한 시도 상한, 미노출을 통과로 치지 않음), 강제 부하기 포화·스크레이프 누락·주입 실패의 무효 처리, 중단 시 하니스가 만든 자원 정리와 부분 기록, 부분 런 셋 리포트, 고정 이미지 불일치 거부, 판정 fixture.
  - 리포트 fixture 검증 항목: 부분, 무효, 불변식 위반, 지원하지 않는 버전, 출력 결정성(두 OS에서 같은 바이트).
  - 자체 검증 시나리오는 짧게 돌리고 비교 결과와 구분해 표시한다. 검증한 OS·CPU 플랫폼을 지원 목록에 적는다.
- Rejected: 판정 fixture와 리포트 단위 시험만 → 컨테이너 중단, 관측 누락, 정리 실패 같은 경계를 검증할 수 없다 · Windows만 필수 → 사용자가 두 호스트를 모두 쓴다

## D-20 절대 일어나면 안 되는 것
- Status: settled
- Decision: 아래 중 하나라도 일어나면 하니스가 실행을 막거나 해당 시도·런 셋을 무효로 표시해야 한다. 이 목록은 다른 결정의 요약이며 어떤 입력에서도 성립해야 한다.

  - 결측(null)을 0으로, 또는 0을 결측으로 그리거나 집계하는 것 (D-12, D-15)
  - 기존 결과를 덮어쓰거나, 정리에 실패한 상태를 다음 시도에 재사용하는 것 (D-6, D-9, D-13)
  - 하니스가 사용자의 가설, 해설, 결론 내용을 만들어 넣는 것 (D-15, D-16)
